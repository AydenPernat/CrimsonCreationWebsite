# Enable Google and GitHub

The server already implements both OAuth flows, account creation, and existing account sign-in. Buttons activate when the corresponding client ID and client secret exist. Credentials cannot be generated by the website; register the apps in your accounts first. Keep secrets only in `.env` for local development and Render's Environment settings for production.

## Google

1. Open [Google Cloud Console](https://console.cloud.google.com/). Select/create a project, then open **Google Auth Platform**. Configure Branding, Audience, and Data Access (basic `openid`, email, and profile scopes).
2. Under **Clients**, create an OAuth client of type **Web application**. Add this authorized redirect URI:
   `https://www.crimsoncreations.dev/api/auth/oauth/google/callback`
3. For your current local preview, add this second URI:
   `http://127.0.0.1:3001/api/auth/oauth/google/callback`
   If you browse with `localhost` instead, add `http://localhost:3001/api/auth/oauth/google/callback` and use that origin in the local configuration.
4. Copy the client ID and client secret into `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in Render's Environment page (and your local `.env` if testing locally).
5. Add your Google account as a test user while the app is in testing. Follow Google's production publishing requirements before offering sign-in to all visitors. Restart locally or redeploy Render after changing environment values.

[Google's official server OAuth guide](https://developers.google.com/identity/protocols/oauth2/web-server)

## GitHub

1. Open [GitHub Developer Settings → OAuth Apps](https://github.com/settings/developers), then choose **New OAuth App**.
2. Application name: `Crimson Creations`. Homepage URL: `https://www.crimsoncreations.dev`. Authorization callback URL:
   `https://www.crimsoncreations.dev/api/auth/oauth/github/callback`
3. Generate a client secret. Add the app's values as `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` in Render.
4. Create a separate development OAuth app with homepage `http://127.0.0.1:3001` and callback `http://127.0.0.1:3001/api/auth/oauth/github/callback`. Put this development app's credentials in your local `.env`.
5. Restart locally or redeploy Render. Test **Continue with GitHub** using an account with a verified email.

[GitHub's official app registration guide](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app)

## Local versus production settings

Local `.env` for the URL you were viewing:

```dotenv
PORT=3001
CRIMSON_PUBLIC_URL=http://127.0.0.1:3001
GOOGLE_CLIENT_ID=your-google-client-id
GOOGLE_CLIENT_SECRET=your-google-client-secret
GITHUB_CLIENT_ID=your-development-github-client-id
GITHUB_CLIENT_SECRET=your-development-github-client-secret
```

On Render, use `CRIMSON_PUBLIC_URL=https://www.crimsoncreations.dev` and the production GitHub credentials. Redirect URIs must match the public URL exactly, including `www`, `localhost` versus `127.0.0.1`, and the port. If the production site uses the apex domain instead, change the public URL, canonical links, schema URLs, sitemap template URLs, and registered callbacks together.

New Google/GitHub users get a verified portal account. Existing password accounts should sign in once with their password, then choose **Connect Google or GitHub** inside their dashboard, using the same verified email. This protects existing accounts from silent email-based merging.

## Free spam protection

The hidden honeypot field is self-hosted code, not a paid service. It has no subscription, yearly renewal, API key, or challenge quota. It stays active as long as the form/server code is deployed. The server also limits valid requests to five per IP per hour. Honeypots catch simpler bots; no technique stops every bot.

If you later want stronger challenge-based protection, [Cloudflare Turnstile's current free plan](https://developers.cloudflare.com/turnstile/plans/) includes unlimited challenges. It is optional and is not enabled in this release.

## Sitemap and studio schema

Deploy the root `sitemap.xml` alongside the updated server and HTML/assets. The server serves the file at `/sitemap.xml` and appends published project URLs. `robots.txt` points Google to that endpoint. The homepage has one ProfessionalService JSON-LD block with the existing logo image; it omits unverified example social profiles.

This workspace is not currently a Git checkout, so it cannot push changes to an existing GitHub repository as-is. Copy the changed source into your actual repository checkout, review the changes without including `.env`, `data.json`, or `node_modules`, then commit and push that repository. Render can auto-deploy the connected branch. Include `sitemap.xml`, `server.js`, `social-auth.cjs`, `account-tools.cjs`, `script.js`, `enhancements.js`, `style.css`, and the changed HTML files.

After deployment:

1. Confirm `https://www.crimsoncreations.dev/sitemap.xml` and `/robots.txt` load.
2. Open [Google Search Console](https://search.google.com/search-console), add/verify a domain property for `crimsoncreations.dev` using the TXT record Google gives you in Porkbun's DNS settings. If already verified, use your existing property.
3. In **Sitemaps**, submit `https://www.crimsoncreations.dev/sitemap.xml` (or `sitemap.xml` for a matching URL-prefix property).
4. Use URL Inspection for the homepage and request indexing if available. Use [Schema.org's validator](https://validator.schema.org/) to check the ProfessionalService markup. Google Rich Results Test may not offer a special rich-result preview for this type.

A sitemap helps discovery; it does not guarantee instant indexing. Structured data helps Google understand the studio; it does not formally register a business or guarantee a Knowledge Graph entry. [Sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview), [structured data guidance](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data).

## Portal updates

Project logos are optional: upload PNG/JPG/WebP (up to 5 MB, resized before saving) or use an HTTPS image URL. Empty logos retain the droplet. Accounts show connected providers. Social accounts can request an email link to set a separate portal password; provider passwords are never shared with the site. Password sign-in and OAuth use browser-session cookies instead of seven-day persistent cookies. Opening or refreshing the portal ends the previous sign-in. A freshly completed OAuth or magic-link sign-in may enter the dashboard once; returning requires a new sign-in. Verification emails now require an explicit sign-in afterwards. Existing persistent cookies are replaced at the next sign-in; sign out once to clear an old session.
